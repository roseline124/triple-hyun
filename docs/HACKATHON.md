# Ambition for Korea 현장 운영 규칙

## 1. 문제 정의

목표는 프론트엔드 개발과 짧은 기획을 통해 실제 사용자 가치가 보이는 MVP를 조기에 확보하고,
한 번뿐인 제출을 준비된 상태에서 하는 것이다. 기능 수와 코드 양은 성공 지표가 아니다.

공식 안내 확인: 2026-10-24, https://bloomworld.ai/community/ambition/

공식 확인 사항:
- 개발·1차 심사: 10:00~17:00. 제출 순서대로 심사, 팀당 제출 1회이며 재제출 불가.
- 제출물: 데모 링크와 2장 이내 발표 자료. 통과 8팀이 차면 즉시 마감, 잔여 자리는 현장 스크린에 표시.
- 결선: 19:00~20:30, 팀당 발표와 질의응답을 합쳐 10분. 20:30부터 VC와 상호 매칭, 매칭 보장 없음.
- 미션 공개: 09:40. 팀은 2~4인. 1인당 지급 크레딧 $500 범위에서 작업하며 소진 후 개인·회사 계정 사용 불가.

공개 페이지에는 심사 세부 배점, 결선 발표/Q&A의 정확한 분할, 제출 링크 교체 허용 여부가 없다.
아래 시간표와 판단 기준은 **팀의 전략적 가정**이며 공식 배점·합격 기준이 아니다.

## 2. 방향 추천

일찍 완성하고, 품질 기준을 넘은 뒤 잔여 자리를 보고 제출한다.
'극초반 심사는 더 엄격하다'는 확인된 규정이 아니다. 시간대만으로 제출을 늦추지 않는다.
중간 시간대를 기본 목표로 삼되, 자리가 빠르게 줄면 보완 범위를 즉시 줄인다.

10:00 시작 기준의 내부 목표:

| 시각 / 경과 | 확인할 결과 |
| --- | --- |
| 10:00~10:20 / +0~20분 | 사용자·문제·미션 적합성, 팀 스택, 핵심 시연과 제외 범위 합의 |
| 10:20~11:30 / +20~90분 | 입력→AI→결과 첫 흐름, 서버 키 보관, 프론트/백엔드 계약 |
| 11:30~12:00 / +90~120분 | 첫 공개 배포, 실제 AI 호출, 대표 입력, 로딩/실패 상태 |
| 12:00~12:30 / +120~150분 | 핵심 흐름 기능 동결, 가치가 보이도록 UI·문구 개선, 2장 초안 |
| 12:30~14:00 / +150~240분 | 반복 시연·자료·공개 URL 확인 후 제출 검토. 준비되면 더 일찍 제출 가능 |
| 제출 후~17:00 | 심사본 고정, 결선용 설명과 증거 정리. 필수 결함 외 새 기능 제한 |
| 17:00~19:00 | 운영진 발표 규칙 확인, 10분 발표+Q&A 리허설, 백업 준비 |

잔여 자리 확인 담당자 한 명을 정한다. 30분마다 확인하고, 자리가 줄기 시작하면 10~15분마다 본다.
아래 숫자는 공식 기준이 아닌 내부 경보선이다.
- 5~8자리: 준비 기준을 넘으면 제출 검토. 단순히 중간 시각을 기다리지 않는다.
- 3~4자리: 새 기능 즉시 중단, 치명 오류·시연·자료만 고친 뒤 준비되면 제출.
- 1~2자리: 필수 조건 통과 시 즉시 최종 승인 요청. 미통과면 실패 항목과 시간을 공개한다.
- 0자리: 추가 제출 가능 여부를 운영진에게 확인한다. 진출 가능하다고 말하지 않는다.

## 3. MVP 범위

사용자 한 종류, 고통 하나, 대표 입력 하나, 유용한 결과 하나, 화면 최대 3개.
AI가 결과의 어느 부분을 만들어 가치를 주는지 시연 중 설명할 수 있어야 한다.
모델 응답의 그럴듯함보다 실제로 다음 행동을 할 수 있는 결과를 만든다.

예외 없이 실사용 경로를 남긴다. 사전 생성 결과·샘플·녹화는 백업으로 구분한다.
데이터가 부족하면 인터뷰·관찰·가정·추정 수치를 분리한다. 가짜 고객·매출·절감률을 만들지 않는다.
인증/결제/관리자 화면/대규모 데이터 수집은 핵심 문제의 필수 조건일 때만 넣는다.

## 4. 개발 에이전트 작업

`/hackathon-plan`으로 `docs/PROJECT.md`를 생성하고 아래 역할을 팀원에게 배정한다.
- 프론트: 핵심 화면, 상태 처리, 백엔드 계약, 시연 UX, 반응형 확인.
- AI/백엔드: 실제 Claude 호출, 응답 스키마, 제한/타임아웃/실패 처리, 서버 비밀 관리.
- 제품/제출: 문제 근거, 자료 2장, 잔여 자리, 제출 창구, 시연 대본. 소규모 팀에서는 겸임.

15~30분 작업 단위로 담당자·파일·완료 조건을 정한다. 스택과 데이터 계약부터 고정한다.
첫 배포는 완성 후가 아니라 초기에 한다. 최종 제출은 사용자 승인 후 한 사람이 수행한다.

## 5. 검증 체크리스트

`/demo-gate <배포 URL> 현재 시각 ... 남은 자리 ...`로 검토한다.

- [ ] 비로그인 새 브라우저에서 공개 URL을 열 수 있다. 배포 보호와 API 키 노출이 없다.
- [ ] 실제 핵심 AI 흐름을 대표 입력으로 2회 반복했다. 결과의 유용성을 설명할 수 있다.
- [ ] 입력 오류·느린 응답·실패·재시도·새로고침을 확인했다.
- [ ] 타입 검사·린트·관련 테스트·프로덕션 빌드의 결과와 미검증 항목이 기록됐다.
- [ ] 390px 화면과 키보드 주요 동작, 주요 화면의 읽기·대비·포커스를 확인했다.
- [ ] 2장 이하 자료와 데모 URL이 최종본이다. 제출 방식·파일 형식은 현장에서 확인했다.
- [ ] 90초 시연: 문제 15초 → 실제 동작 50초 → 결과·차이 15초 → 한계·다음 검증 10초.
- [ ] 백업 영상/캡처·샘플 입력을 준비했고 라이브 시연과 구분한다.
- [ ] 현재 시각·남은 자리·제출 담당자를 확인했고 최종 승인을 받았다.

자료는 `/hackathon-pitch`로 준비한다. 사업기획은 길게 쓰기보다 한 페이지로 쟁점을 압축한다.
1장: 누구의 어떤 문제인지, 기존 대안, 왜 지금, 해결 가치.
2장: 실제 제품 화면과 전후 차이, 관찰/측정 근거, 시장·수익모델 가설, 팀·링크·한계.
현장 양식이 있으면 그 형식을 따른다. 별도 표지로 한 장을 낭비하지 않는다.

결선은 전체 10분 안에 발표와 질의응답을 넣는다. 분할은 현장 지시 우선이며,
내부 리허설은 4분 설명/시연 + 6분 질문 대응으로 시작한다.
예상 질문: 누가 돈을 내는가, 현재 대안보다 나은가, AI가 꼭 필요한가, 정확도·지연·비용은,
데이터를 어디서 얻는가, 첫 고객은 어떻게 만나는가, 오늘 검증한 것과 아직 가정인 것은 무엇인가.

## 6. 위험

- 자리 소진: 시간만 기다리지 않고 담당자가 실시간 확인한다.
- AI 불안정: 짧은 대표 입력, 서버 타임아웃과 재시도, 정직한 백업을 준비한다.
- 통합 지연: 요청/응답/오류 계약을 먼저 고정하고 첫 90분 안에 연결한다.
- 크레딧 혼동: 개인 Pro와 행사 Console을 구분한다. 조직·잔액 확인 전 모델 호출을 하지 않는다.
- 비용: 30~60분마다 Console 사용량을 기록한다. 개발과 제품 API 사용 모두 계산하고,
  잔액의 약 20%는 시연/결선 예비로 남기는 것을 팀 가이드로 삼는다. 자동 하드 제한은 아니다.
- 사전 제작 규정: 현재는 도구·문서만 준비한다. 미션별 제품의 사전 제작 허용 여부는 운영진에게 확인한다.
- 네이티브 환경: 현재 Xcode 시뮬레이터와 adb가 없어 설치 스킬만으로 네이티브 검증이 되지 않는다.
- 과장된 사업성: 출처·날짜·관찰과 가정을 명시한다. 공식 배점이 공개되지 않았다면 추정이라고 쓴다.
